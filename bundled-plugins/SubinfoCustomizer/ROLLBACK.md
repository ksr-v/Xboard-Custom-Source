# 回滚与异常恢复

仅适用于本文固定 commit 的 aaPanel + PHP 8.3 PHP-FPM 隔离站点。操作前确认实际站点目录、站点用户、PHP 路径和数据库，先保存当前状态。

## 正常恢复

1. 后台“插件管理”禁用 SubInfoCustomizer。该操作移除唯一核心桥接并停止菜单注入；四个默认插件保持启用。
2. 重新请求订阅，检查原生流量、到期与过滤提示。刷新后台，检查原有入口。
3. 需要卸载时再点击卸载。不要卸载四个默认插件，不要用整个旧 Admin 文件覆盖当前资源。

禁用保留 `subinfo_customizer_settings`，重新启用后恢复已保存配置。需要导出时仅备份此表；完整灾难恢复同时备份主数据库与 `.env` / `APP_KEY`。

原生“卸载”不删除 `plugins/SubinfoCustomizer/` 私有源码。确认已卸载后，可用原生“删除插件”移除源码。`storage/framework/xboard-admin-patch.lock` 是默认插件共用的锁文件，应保留。

## 安装预检失败

主仓库安装器先执行插件迁移，再开始插件记录事务并调用 `install()`。因此版本或权限预检失败时，即使后台仍显示未安装，本插件空配置表和迁移记录也可能已经存在。先修复不匹配原因，再通过原生安装操作重试；不要重跑整个面板安装或清空主数据库。

若决定放弃安装，先确认插件记录不存在、没有自有核心桥接且已备份本插件表，再仅清理 `subinfo_customizer_settings` 和 `2026_10_27_000001_create_subinfo_customizer_settings` 对应迁移记录。不要执行不限定路径的整批 `migrate:rollback`。

## 版本或补丁异常

本插件拒绝对未知控制器或损坏标记写入。启用失败后保持禁用，先查看 `storage/logs/` 中 SubInfoCustomizer 的错误。原生禁用器也会先把本插件标记为禁用，再执行 `cleanup()`；即使清理返回错误，不能仅凭错误提示判断插件仍在启用，应核对实际记录与核心文件。不要删除版本校验来继续启用。

如果禁用过程中遇到其他来源对控制器的修改，停止自动移除。核对当前文件，手动只删除从 `// <subinfo-customizer-core-v1>` 到 `// </subinfo-customizer-core-v1>` 的完整七行，保留其他所有内容。执行 PHP 8.3 `-l` 检查，再请求原生订阅验证。没有确认其他改动前不要还原整个文件。

无其他核心修改时，可核对干净控制器的 LF 归一化 SHA-256：`3303d9696a44268e42e0f39371ff42aed87597da68d207c0847fccb98d270ece`。本站验证使用的 PHP 路径为 `/www/server/php/83/bin/php`。

若 PHP-FPM 的 OPcache 配置不检查文件时间，按 aaPanel 对该站点对应的 PHP 8.3 服务执行重载后验证。先核对正在使用的 pool，避免误操作其他站点。

## 升级失败

原生上传器会先删除旧插件源码再复制新源码；原生升级器会先禁用插件，再迁移、执行更新和启用。这些步骤不构成完整文件与数据库事务。

升级前保存完整插件目录和数据库。失败后保持本插件禁用，恢复可信的旧 `plugins/SubinfoCustomizer/` 源码和与之对应的本插件版本记录；先核对配置表仍完整，再启用。涉及未来版本数据库结构变更时，按该版本迁移说明恢复，不能仅靠复制旧源码回滚数据库。不要修改其他插件记录。

## 卸载迁移批次边界

主仓库使用 Laravel 原生 rollback，并指定本插件迁移路径。如果最后一批迁移包含本插件，该表会由本插件 `down()` 删除；如果之后有其他插件迁移占用了最后批次，本插件表可能保留。此时保留表可用于恢复，不会参与已卸载插件的订阅处理。

如需彻底清理，先确认本插件已卸载、保存本插件表备份，再由数据库管理员删除 `subinfo_customizer_settings` 及该迁移对应记录；不要按批次删除其他迁移或其他插件表。再次安装前确认该表与迁移记录一致。
